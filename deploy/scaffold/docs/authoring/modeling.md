# 把业务整理成服务 · 划分指南（先读这份，再读 `service.md`）

> **这份回答「该写哪些服务」，`service.md` 回答「怎么写一个服务」。**
> 顺序不能反：先把形态定下来，再动第一行代码。形态错了，`service.md` 的每一条你都能做对，
> autocheck 也会全绿——**门禁查的是 wire 契约，不是设计**。一套划分错误的服务可以完全合规。
>
> 用法：按 §1 → §2 → §3 走一遍，产出一张「服务 × 实体」表，然后去 `service.md` 落地。
> AI 执行时：§2 的三个判据都是**是非题**，不要用「视情况而定」作答；§4 的数字只是体检信号，不是规则。

---

## 0. 第一原则：最省事的划分是不划

新建一个服务的成本不只是写代码——它还要端口、要 `services.json` 一行、要 introspection ↔ 注册同步、
要自己的 GUIDE.md、升级时要跟着走。**能不新建就不新建。**

动手前先把需求里的名词对着下表扫一遍，命中的部分**直接用，不要重造**：

| 你的需求里出现 | 已经有了 | 别自己写 |
|---|---|---|
| 账号、登录、会话、谁能调什么 | **user** | 别建 `account` / `auth` 服务 |
| 上传文件、存图片、附件 | **storage**（CAS，SHA-256 去重） | 别建 `file` / `upload` 服务 |
| **大文件**（>~3.7MB：视频、压缩包、导出件） | **storage 的占位资产**（`storage.asset.external`）+ 字节你自己存 | 别建并行的存储服务，也别去改 storage —— 见下方 ★ |
| 发通知、站内信、消息要重试 | **notification**（已带退避重试 + 死信队列） | 别自己写重试循环 |
| 发邮件 / 发短信（**出站**） | **gateway** | 别直接 `require('nodemailer')` |
| 接第三方回调 / webhook（**入站**） | **ingress**（API key + 去重） | 别自己开 HTTP 口收 |
| 要人点头才能继续 | **approval**（request→verify→confirm→reject，支持多签） | 别写 `status: 'pending_review'` 土审批 |
| 多步骤、有条件分支的流程 | **orchestrator**（工作流模板 + 执行） | 别写一长串 if/else 编排 |
| 「发生 X 就自动做 Y」 | **nexus**（事件订阅式反应体） | 别写轮询循环 |
| 调大模型 | **agent**（Gemini/Qwen/OpenAI，能力路由） | 别在自己服务里塞 SDK |
| 日程、待办，以及任何**业务实体**的增删改查 | **你自己的服务**（`api/apps/<你的服务>/`，用 Entity Factory） | 框架**没有业务层**，别在框架里找。曾有个 `planner`（日程/待办）随栈下发，那是历史遗留、已废弃，新项目不再带它 |

### ★ 大文件：storage 收不下，但也不要自己另起一套

`storage.asset.upload` 收的是 **base64 字符串**，声明上限 5,242,880（原文件 **~3.7MB**），
且要穿过 Router 的 10s 转发超时。视频、压缩包、数据库导出这类东西**塞不进这条路**。

这时候很容易走上三条弯路，**三条都别走**：

1. ❌ **自己写一套存储服务** —— 要重新实现 CAS、去重、缩略图、visibility、驱动抽象，
   还要自己配一套对象存储凭证；而且业务实体从此有两种文件引用方式。
2. ❌ **去改 storage** —— 它是 `[Solo]` 只读区（派生项目里只有编译后的 bundle，
   没有源码），改了也会被下次 `upgrade.sh` 覆盖。
3. ❌ **想办法把上限调大** —— 上限不是瓶颈，路径才是：base64 膨胀 33%、Router 10s 超时、
   payload 在内存里存三份。调大只是把墙往后挪一点。

✅ **正确做法：字节你自己存，指针登记到 storage**

```
你的服务保存文件 → 对外给一个 http(s) URL
   ↓
storage.asset.external { url, filename, mimeType, size, visibility }
   ↓
拿到 assetId —— 业务实体照旧用 assetIds 挂引用，下游取数写法完全不变
```

**分片、断点续传、进度、CDN 全部由你决定**——框架刻意不做这套，因为各家需求形态差太远
（视频 / 数据库导出 / 设计稿完全不是一回事）。框架只保证那个**引用身份**是统一的。

⚠️ 换来的代价，用之前先看清（完整对照表见 `system.guide storage` 的「配方一之二」）：

- **storage 只给指针，不返回字节**——客户端拿到 URL 后直接去你的服务取，storage 不代理转发。
- **字节面的访问控制归你**——`visibility` 只挡「谁能拿到这个指针」，URL 发出去之后
  storage 不在字节路径上，管不了。
- **`size` 是你申报的，`sizeVerified:false`**——别拿它计费或做配额。
- **无 sha256 去重、无缩略图**——两次登记同一个文件 = 两个资产。
- **指针会悬空**——你删了自己那份文件，storage 的记录还在、`resolve` 照样返回死链。
  删文件时记得一并 `storage.asset.delete`。
| 状态机式履约推进 | **fulfillment**（声明式 JsonLogic） | 别手写状态流转 |
| 数据要**从网页里取**、动作要**落回网页上**（人在浏览器里干活） | **`client/extension-kit/`**（传输/重试/持久化队列/图片规格化/会话，见 `client/README.md`） | 别自己写扩展的 RPC 与重试 |

> 扫完还剩下的名词，才是你**真正要建模的东西**。多数项目扫完会发现只剩下 1–3 个真业务服务。

## 1. 第一步：把名词列出来，分成三堆

把需求描述里所有名词抄下来（不要提前合并、不要提前分层），然后分三堆：

- **A 堆 · core 已覆盖** —— 上表命中的，划掉。
- **B 堆 · 真业务概念** —— 你这个项目独有的东西。
- **C 堆 · 属性** —— 用 §2.1 判出来的，它们不是实体，是别人的字段。

只有 **B 堆**参与后面的划分。

> ⚠️ **别从「要几张表」开始。** 最常见的走偏就是一上来先建五张空表再想业务往里填什么——
> 症状是每个实体都只有 CRUD、没有任何其他方法（见 §4 体检信号）。
> 建模的起点是**动作**（这个系统要做什么），不是**存储**。

## 2. ★ 三个判据（全是是非题）

### 2.1 判据一：它是实体，还是字段？

对 B 堆里每个名词问三句，**三句都答「否」就不是实体**：

| 问 | 答「是」的含义 |
|---|---|
| 它能**单独被创建**吗（不需要先有别的东西存在）？ | 有独立生命周期 |
| 宿主还在的情况下，它能**单独被删除**吗？ | 生命周期不依附 |
| 它需要被**单独列表 / 检索**吗？ | 有独立的查询面 |

**举例**：订单的「收货地址」——不能脱离订单创建、订单没了它就该没、也不需要单独列地址表 ⇒
三问全「否」⇒ **它是订单的字段，不是实体**。而「商品」能单独建、单独删、要单独列表 ⇒ 是实体。

> 判错的代价是实打实的：每个实体要 `logic/<entity>.js` + introspection 声明 + entities schema
> 三处同步（`service.md §3`），把字段当实体建，这套开销白付，还多出一堆没人调的 CRUD 方法。

### 2.2 判据二：这些实体该合成一个服务，还是分开？

**用框架的硬约束来判——「服务之间禁止直接互调」（只能走 Router 或 `_tasks`）。**
这条红线不只是限制，它是**最好用的划分工具**：

> 写出这个系统 **3 个最典型的用例**，逐个数：完成它需要几次跨服务往返？
>
> - **0–1 次** ⇒ 划分合理。
> - **≥2 次，且每次都是同一批服务一起出现** ⇒ **它们应该是一个服务。**

理由很直接：跨服务的每一跳都要经 Router 转发 + 签名校验，还拿不到事务。
**两个总是一起被读写的概念分在两个服务里，等于给自己造了一个永久的分布式事务问题。**

### 2.3 判据三：它能被单独摘掉吗？

反过来验证「该不该拆出去」：

> 把它从 `deploy/services.json` 里删掉，其余服务还能起来、核心用例还能跑通吗？
>
> - **能** ⇒ 它是独立能力，可以是自己的服务。
> - **不能** ⇒ 它是别人的一部分，别拆。

§2.2 防的是「拆得太碎」，§2.3 防的是「粘得太死」。两条都过，划分才站得住。

## 3. 第三步：产出一张表，然后去写代码

定型的产物就是这么一张表——**先把它写进项目的 `docs/`，再动代码**：

| 服务 | 实体 | 它负责回答的问题 | 为什么不并进别的服务（§2.2 数字） |
|---|---|---|---|
| `{{PROJECT_NAME}}` | widget, category | 「有哪些 widget、它们怎么分类」 | 典型用例 0 次跨服务 |
| … | … | … | … |

有了这张表，`service.md` 的每一节都变成机械操作：一个服务一套文件（§1）、一个实体改三处（§3）、
命名照 `{service}.{entity}.{action}`（§5）。


### ★ 时间字段：一律 epoch ms，例外必须声明

**存的是数字**（`Date.now()` 那种毫秒整数），不是 `"2026-09-04T00:00:00Z"` 这种 ISO 字符串。
Entity Factory 自己盖的 `createdAt` / `updatedAt` 就是数字，你自己加的时刻字段跟着它走。

为什么值得单列一条：**混形态不会报错，只会静默算错**。三种形状都实测过——

| 写法 | 拿到 ISO 串时 | 拿到数字时 |
|---|---|---|
| `now - rec.createdAt` | `NaN` | 正常 |
| `arr.sort((a,b) => b.createdAt - a.createdAt)` | 比较器返回 `NaN` ⇒ **`Array.sort` 变 no-op**，「最新在前」退化成无序 | 正常 |
| `Date.parse(rec.createdAt)` | 正常 | **`NaN`**（`Date.parse` 只吃字符串） |
| `zAdd({ score: rec.createdAt })` | score 落 `NaN` / 0 | 正常 |

四种都不抛异常、不进日志、单测也照样绿——只在真数据上错。

**`handlers/entities.js` 里怎么写**：

```js
"createdAt": { type: "datetime", description: "创建时间" },              // 默认 = epoch ms
"capturedAt": { type: "datetime", format: "iso", description: "…" },    // 例外，必须显式声明
```

`type: "datetime"` 是给 Portal 的**渲染**提示（"按时刻显示"），它不回答"**存**成什么"；
`format` 才是。缺省即 epoch ms。**确实需要 ISO 是合法的**（对接外部契约、迁不动的存量数据），
但必须写出来——写出来它就是被记录的例外，不写就是没人知道的漂移，下一个读它的人照样踩。

**读一个可能是两种形态的字段，别自己写兜底**：

```js
const { toMs, toMsOr } = require('../../library/clock');   // 或 require('../../library/entity')
toMs(v)          // 严格：解析不了就抛，用于「这里绝不该拿到坏值」的边界
toMsOr(v, 0)     // 排序键：解析不了落 0，排最后
toMsOr(v)        // 时间差/新鲜度：解析不了给 null，再显式判空
```

⚠️ 做**时间差**时别用 `|| 0` 兜底：`now - 0` 是个巨大的正数，「24 小时内」会判成 false，
缓存永不命中之类的 bug 就是这么来的。要么 `toMsOr(v)` 拿 null 显式判，要么让它抛。

> 门禁：`autocheck clock-check`。声明成数值时刻却写入 ISO 串、或对数值时刻字段调
> `Date.parse()` ⇒ **ERROR**；时间字段用裸 `Date.now()`（应走 `clock.now()`，可注入、
> 测试可冻结）、或写 ISO 但没声明形态 ⇒ WARN。

## 4. 体检信号（数字是「停下来看一眼」，不是规则）

Solo 框架自身 13 个服务的实测分布，可以当参照系：

| 指标 | Solo 自身范围 | 中位 |
|---|---|---|
| 每服务实体数 | **0 – 4** | 1 |
| 每服务方法数 | 3 – 54 | ~22 |

据此的三个信号——**命中不等于错，等于「该回去过一遍 §2」**：

- **实体数 > 4** ⇒ 大概率一个服务里塞了两个域。（实测 5 个派生项目，出现过 9 个和 12 个实体的服务。）
- **一个实体挂了 > 10 个方法** ⇒ 大概率漏了实体：那些方法里藏着第二个名词。
- **某个实体只有 CRUD、没有任何其他方法** ⇒ 它可能只是张表，不是实体。回 §2.1 重判一次。

**反过来，「实体少但 logic 很长」不是问题信号。** Solo 的 `orchestrator` 是 1 个实体、logic 合计 2856 行——
但那是 **10 个文件的聚合**（最大单文件 853 行），复杂度在**执行引擎**里，不在数据模型里。
**「服务体量」和「单文件体量」是两个指标，别混着看**：前者大只说明这个服务承担的事多，
后者大才是代码组织问题——而后者与实体划分无关。**不要为了「让文件短一点」去拆实体。**

### ★ 要不要拆文件：看变更频率，不看行数

行数是现象，不是判据。真正可判定的判据是**这个文件还动不动**：

```bash
git log --oneline -60 -- <file> | wc -l     # 近 60 次提交里被改过几次
git log -1 --format=%ad --date=short -- <file>   # 最后一次改动
```

拆分的收益**全部落在未来的改动上**（更好定位、更少冲突、测试更易隔离）。
所以：**变更频率是收益的分母，分母接近零，再长的文件也不值得拆。**

> 实例：`orchestrator` 最厚的 `runner.js`（806 行）在近 60 次提交里**只被改过 1 次**，
> 其余四个文件各 1 次、且都停在同一天。这种情况下拆分只剩风险，没有收益。
> 真需要动的时候顺手拆（那时你本来就在读这段代码、测试也要跑），别专门开一刀——
> 这叫**机会性重构**，是这类稳定模块的正确处理方式。

## 5. 四个常见走偏

| 走偏 | 症状 | 回哪一节 |
|---|---|---|
| **表驱动建模** —— 先建五张空表再想业务 | 每个实体只有 CRUD | §1 提示 + §4 |
| **一个服务承载整个域** —— 把「财务」「商品」当成一个服务 | 实体数 9+ | §2.2 |
| **把附属物建成实体** —— 地址、明细行、快照 | 大量没人单独调的 CRUD | §2.1 |
| **重造 core** —— 自己写审批 / 上传 / 重试 | 与 §0 表格重叠 | §0 |
| **为大文件另起一套存储** —— 因为 `upload` 塞不下就自建 file 服务 | 业务实体出现两种文件引用方式 | §0 ★ |
