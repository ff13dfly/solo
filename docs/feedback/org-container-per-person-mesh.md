# 反馈：「每人一箱」用法暴露的五处缺口 —— 只读区其实是治理机制，而 v2 的协调层缺归属人

> 来源：overview 会话，2026-08-20。场景是把 SOLO 用作**一家公司的组织底座**：
> 每个职能岗位（财务 / 推广 / 产品）配一个人 + 各自的 AI，各建一套基于 SOLO 的系统，
> 将来由上层协调层联通。本轮场景的类比是「SOLO 是人机合作的集装箱」。
>
> **依据分三类，请按类采信**：
> - **自查实测**：§1 的 scaffold 下发清单与 5 个派生项目的现状（本机 `ls` + `grep` 核对）；
>   本轮实际为两个节点铺设的过程（finance 协作文档、promo 上手与实体规格）。
> - **源码/文档核对**：`deploy/scaffold/init.sh`、`docs/planning/VERSION.v2.md`（草案，
>   **校对基准 2026-07-15，v2 尚未启动**）、`deploy/scaffold/README.md`。
> - **判断**：§2–§5 是从上述两类推出来的设计意见，**不是运行结果**——跨网格那套今天不存在，
>   无法实测。请当作场景输入而非缺陷报告。
>
> 涉及：`deploy/scaffold/init.sh:191-194`、`docs/planning/VERSION.v2.md` §2.3 / §3 / §4.3。

## 一、【实测 · 最便宜】scaffold 不下发项目根 `CLAUDE.md`，而 5/5 派生项目都自己补了

`init.sh` 只下发守门 skill：

```sh
# deploy/scaffold/init.sh:191-194
mkdir -p "$NEW_DIR/.claude/skills/solo-service"
...
log_info "Copied: .claude/skills/solo-service (authoring guardrail skill — wraps autocheck)"
```

项目根**没有** `CLAUDE.md`。而本机 5 个派生项目全部手工长出了一份：

| overview | finance | trend | colony | runner |
|---|---|---|---|---|
| 有 | 有 | 有 | 有 | 有 |

5/5 补同一个洞，说明这不是个别偏好，是 scaffold 的缺省。

**两者管的不是一回事**，所以 skill 顶替不了：

- `solo-service` skill **只在动 `api/apps/` 时触发**，管的是 wire 契约、autocheck、服务代码规范；
- 项目根 `CLAUDE.md` **每轮会话自动加载**，管的是「这个项目为什么存在」「什么值得做」
  「数据分几类、哪类必须有导出出口」「判断类内容不进库」——这些在写第一行服务代码**之前**就要生效。

**这个缺口在「非程序员 + AI」的用法下会放大成质变。** 本轮给一个**无终端使用经验**的岗位铺 promo
时，真正起约束作用的不是 skill，是那份每轮加载的 `CLAUDE.md`：它拦的是「AI 主动提议加功能」
「一上来就建 CONTACT/CAMPAIGN 五张空表」「不可再生数据只存 Redis 没有导出」这类问题——
skill 一条都拦不到，因为它们不发生在改 `api/apps/` 的时刻。

**建议**：`init.sh` 下发一份 `CLAUDE.md.template`，含占位的「目的 / 判据」段 + 已成型的
通用段（只读区边界、`stage` vs `status`、门禁命令、密钥清单、三类数据待遇、
"框架级问题回写 feedback 而非本地打补丁"）。本轮为 promo 写的那份可以直接当素材，
需要的话我把它整理成模板提过来。

## 二、【判断】v2 Bridge 的规格里缺一个角色：上游协调层的**归属人**

§3 把 bridge 的机制定义得很清楚：SOLO_A 分发到下游 SOLO_{1..n}，认证走 mesh Ed25519 验签、
授权走窄 permit、对 router 零改动。**但"谁有权改 SOLO_A 上那份 permit / bridge 配置"没有定义。**

在「每人一箱」用法下这是最关键的治理问题：

- 上游是**权限汇聚点**——它要能回答跨部门问题，就必须能读所有下游；
- 它的每一次配置变更**同时影响所有下游**（「财务的数据推广能不能看到」不是任何单个节点能决定的）；
- 而现在它和下游自己的配置变更走同一套机制，**没有任何区分**。

§3.6 已经做过一轮对抗式安全评审并列出四处硬缺口，说明这个位置的敏感性是被认识到的；
缺的是把"变更权限"也纳进来。

**建议（成本很低，因为能力已经有了）**：把 bridge 的 permit / 路由配置变更接到
**approval（多签）+ orchestrator 的分层审批治理链**上，与普通服务配置走不同路径。
这两样在 v1.1 已落地，只是没接到跨网格配置面。

## 三、【判断】§2.3 的「同运营者 ⇒ 同信任域」假设，在部门场景下不成立

裁决台账里「actor-claim 全量」搁置的理由是：

> 平行网格 = 同一运营者同信任域，mesh 签名的**网格级**归因已够。
> 重启条件：出现跨运营方联邦（下游网格属于别人）。

**「同一家公司内不同部门各自一套网格」这个场景，运营者是同一个，信任域却未必是同一个。**
财务与推广之间存在真实的信息隔离需求，这不是"跨运营方"，但网格级归因
（只知道请求来自 `SOLO_财务`）可能不够——需要知道是**谁**发起的，尤其当上游那个协同 AI
可以代表任意下游发起调用时。

**建议**：把「同运营者内的部门级隔离」作为一个**显式场景**补进 §2.3 的重启条件判断，
不要隐含在"同信任域"里。它是否触发 actor-claim 重启可以再议，但目前的措辞会让人
直接跳过这个场景——因为它两头不靠：既不是"平行处理分担负载"，也不是"跨运营方联邦"。

## 四、【判断】B 线（部署瘦身）在这个场景里是**可行性前提**，不只是优化

§3.1 自己写了：每租户一套独立网格「代价是运维更重（N 租户 = N 套部署）」。

在「每个员工 + AI 一套」的用法里，**N 就是员工数，而这些人不是运维**。本轮的实测参照：
给一个无终端使用经验的岗位铺一套栈，门槛落在 Homebrew / node / redis / Claude Code 四样依赖，
外加 redis 归属校验、端口分配、密钥生成这些该岗位无法自己判断的环节——
**最后的解法是由已有环境的机器生成好整包交付，该岗位本机不跑 `init.sh`。** 这条路能走通，
但它不 scale：每加一个人就要有人替他做一次。

**建议**：在 B 线的价值论证里补上这个场景。目前 §2.2 / §4.3 把它论述成"告别固定全量 bundle"
的部署优化；在组织底座这个用法下，它决定的是**一个非技术岗能不能自己拥有一套网格**——
这是可行性，不是优化。

## 五、【判断 · 定位】只读区的真正价值是治理，而文档只说了升级安全

现在的措辞（`deploy/scaffold/README.md`、upgrade 相关文档）是从**升级**角度讲的：
`[Solo]` 标记的文件升级时整体覆盖，`[Project]` 的不动；改了只读区"升级就没了"。

但在多人多网格的用法里，只读区实际承担的是另一件事：**"标准不由使用方调整"的强制执行。**

这正是集装箱能成立的核心——ISO 箱规六十年不变，价值全部来自它不变。一般框架的
"最佳实践"只是文档里的一句话，改了不会有任何后果；**SOLO 的只读区有后果**，
所以它是真的标准，不是建议。配套的执行细则（框架级问题回写 feedback 上收，
而不是本地打补丁）已经跑通并产出过 v1.1.14 的几项改进。

**建议**：在 README / VERSION 里把只读区**显式定位成治理边界**，而不只是升级机制。
这对"SOLO 用作多人协作底座"这个方向是最强的一句话——**它是唯一能保证
"每个人的 AI 不会各自发明一套约定"的东西**，而这恰恰是 AI 辅助开发规模化时的头号风险。
现在这个卖点埋在升级章节里，读者不会自己推出来。

## 建议排序

1. **§1 scaffold 加 `CLAUDE.md.template`** —— 实测证据最硬（5/5 派生项目自补），成本最低，
   对"非程序员 + AI"用法收益最大。
2. **§2 bridge 配置变更接 approval / 治理链** —— 能力现成，只差接线；且属于 v2 设计期
   最好改的窗口。
3. **§5 只读区定位上收进文档** —— 零代码，纯定位。
4. **§3 §2.3 补部门级隔离场景** —— 只需改措辞与判断条件，不必现在就决定是否重启 actor-claim。
5. **§4 B 线价值论证补场景** —— 影响优先级排序，不影响当前实现。
