## 一、【场景】这块试验田正好落在规格排的「最轻档」上，而且有持续流量源

- 全部网格同运营者、同信任域：actor-claim、fieldmask 两块条件件（§3.4-②④）都不触发，
  与裁决台账「先做同运营者平行网格」的排序**互相印证**——规格排的顺序有了第一个真实用户。
- 下游里有 colony（K 线节拍驱动、不可停）：bridge 一旦接进它的链路，联邦层就有
  **和事件总线同款的持续真实压力**，不是打一次通了就算的验收测试。
- 试验的第一条航线选的是 overview → runner（捕获条目派发为任务）：货现成、
  且**两网格同在一台机器上**——这引出 §2 的建议。

## 二、【判断】建议把「同机跨网格（loopback bridge）」定义成 A 线的第一个里程碑形态

§3.4-④ 把多机 TLS 列为 bridge 硬前置。但试验田的第一条航线（overview → runner）
两个 Router 在同一台机器的不同端口上——**跨网格（独立 Router / Redis / keypair）但不跨机**。
这个形态下 TLS 前置天然不触发，信封签名 / 窄 permit / 环路刹车 / 能力表预检
**全部照常需要、照常可测**。

**建议**：在 §3.4 或里程碑规划里显式承认这个中间档。价值：A 线可以在多机 TLS
落地之前就开始被真实使用和证伪，而不是让整条线等一个传输层前置；
同时避免实现者把「同机」误当「同网格」而跳过签名与 permit（loopback 可信是
v1.1 的单网格假设，跨网格后哪怕 loopback 也不该继承它）。

## 三、【判断 · 实测支撑】联邦握手需要暴露版本，否则版本漂移会被误诊为联邦 bug

2026-08-23 现扫，各派生项目 bundle 版本：steward / runner v1.2.1、colony v1.1.15、
overview / finance / trend v1.1.14、wavely/erp v1.1.12、ladder v1.0.0（solo 最新 tag v1.2.1）。
**第一条航线（overview → runner）就已经横跨 v1.1.14 / v1.2.1。**

单网格时代版本漂移只影响自己；联邦后它变成**两个网格之间的不对称**，而 §3.3 的
预检（缓存下游 `system.capability.list`）目前只看方法存在性与 schema——
下游 bundle 版本不在握手信息里。试验田会先靠人肉 `upgrade.sh` 对齐绕过，
但这不 scale 到公司侧（下游网格属于别人时，你无权替对方升级）。

**建议**：capability 握手（或信封）里带 bundle 版本 / 协议版本，bridge 侧提供
「版本不齐时 fail fast 或至少 log」的判据。成本低（capability.list 已是握手第一步），
换来的是把「联邦问题」和「版本差」在第一现场分开。

## 四、【文档核对 · 复述】§3.6 A 组四缺口里，有两处在这个最轻档照样成立

不是新发现，是把安全评审结论对到这块试验田上，供排期参考：

- **#1（信封缺 `aud`）**：自家 mesh 全是登记同一把公钥的平行网格——正是该缺口
  描述的重放形状。试验田网格越多，洞越大。
- **#4（public 方法绕过窄 permit）**：下游各网格的 public 面（含 passport 自助发证）
  对能触达 Router 的 peer 敞开，federation-public ≠ public 需要在第一条航线接通前立起来。

#2（actor 当授权输入）/#3（callee 未钉定）在同信任域烈度下降，但试验田若如期长到
steward ↔ finance（finance 跑在第三方服务器上），#3 会先回来。

## 建议排序

1. **§3 握手带版本** —— 成本最低（capability.list 已是握手第一步），且试验田第一条航线
   当场就会用到。
2. **§2 同机跨网格里程碑** —— 纯规划文档改动，让 A 线可以先于多机 TLS 开始被证伪。
3. **§4 无新增动作** —— 仅确认 A 组 #1/#4 的排期优先级有了真实场景背书。
